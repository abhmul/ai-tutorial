Main question: can examples from the author's local agent setup be safely presented as general setup instructions for people with no AI experience?

Plain terms

Terms used in the review

Model and harness

Model means the AI system that predicts and generates text. Harness means the surrounding program that lets the model read files, run commands, edit files, and ask for permission.

Hook

A hook is a script or extension that runs at a specific moment, such as before a shell command. In this repo, hooks are used as accident guards.

Sandbox

A sandbox limits what a tool can touch, such as files, network, or system commands. Hooks do not replace sandboxing.

Subagent or worker

A subagent or worker is a separate agent session assigned a smaller task. Different tools implement this differently.

Main finding

Useful examples, not drop-in setup

The beginner-facing path is sound: start with chat tools, try one agentic tool on a real project, learn permissions, and keep context clean. The advanced infrastructure should be framed separately.

Keep

High-level learning sequence and source-retrieval norms.

Fix

Stale Codex config example and portable setup instructions.

Explain

Prerequisites, side effects, permissions, and tool-specific behavior.

The risky pattern is not the presence of advanced examples. The risky pattern is presenting local, high-privilege, or tool-specific examples as if they were beginner defaults.

Focus item 1

Codex config and profile guidance needs a freshness fix

Finding

  • The local Codex config snippet uses a profile form that T003 found stale for current Codex docs.
  • T003 reports that Codex 0.134.0+ uses separate profile config files instead of reading [profiles.<name>] from the main config.
  • T003 also reports that features.hooks is the current feature key; codex_hooks is deprecated.

Recommendation

  • Show the current base config separately from any high-privilege profile.
  • Label approval_policy = "never" and sandbox_mode = "danger-full-access" as advanced and elevated risk, not a beginner default.
  • Ask T006 or a later implementation task to verify exact final snippets before editing setup docs.

Primary sources surfaced by T003: Codex advanced configuration, Codex hooks, and Codex approvals and security.

Focus item 2

Web discovery needs prerequisites

Finding

  • The local web-discovery skill requires ketch on PATH.
  • T003 found Ketch docs for search, scrape, code, docs, and backend configuration.
  • The repository does not yet give a newcomer enough setup detail to run that skill reliably.

Recommendation

  • State the functional contract first: find candidate sources, retrieve source text, then cite the retrieved source.
  • Document Ketch setup or mark the skill as local-only.
  • Do not make Brave, Kagi, or any specific backend a hard requirement unless exact setup is documented.

Keep the principle that search snippets are leads, not evidence. This is useful beginner-safe guidance.

Primary sources surfaced by T003: Ketch primary docs, Brave Search API docs, and Agent Skills specification.

Focus item 3

Orchestration is harness-specific

Orchestration means splitting a larger job into smaller tasks and giving those tasks to separate workers or fresh sessions.

Pi

The local orchestration skill dispatches Pi workers through a tmux script. T003 reports that Pi does not have built-in subagents.

Codex

T003 reports that Codex has official subagent workflows and custom TOML agent definitions. These are separate from the Pi worker watcher.

Claude Code

T003 reports that Claude Code has official subagents, while agent teams are experimental and disabled by default.

Portable baseline: write a task file, start a fresh session or official subagent with only the needed context, and require a handoff artifact that records evidence, changes, blockers, and follow-up tasks.

Primary sources surfaced by T003: Pi usage/design docs, Codex subagents, Claude Code subagents, and Claude Code agent teams.

Focus item 4

Hooks are opt-in friction, not security boundaries

Finding

  • The local hooks README documents destructive-command guards for multiple harnesses.
  • The Obsidian guard is a custom confirmation layer for delete-like CLI commands.
  • T003 found official docs distinguishing hooks, permission rules, and sandboxing.

Recommendation

  • Install these hooks only as an advanced, explicit opt-in step.
  • Document prerequisites: Bash, jq, python3 for the Obsidian classifier, and harness-specific hook or extension support.
  • Explain toggle files, project opt-outs, failure behavior, and the temporary Obsidian confirmation file.

A hook can catch many obvious accidents. It does not replace backups, sandboxing, least-privilege permissions, or human review.

Primary sources surfaced by T003: Codex hooks, Claude Code hooks, Claude Code permissions, Pi extensions, and Obsidian CLI docs.

Focus item 5

Use isolated Python environments, not author-local paths

Finding

  • The local audit found examples that use an author-specific shared virtual environment path.
  • That path is useful for the author's machine but is not a requirement newcomers can satisfy by default.
  • T003 found official docs supporting isolated Python environments and tool installers.

Recommendation

  • If Python helpers are shown, give portable alternatives such as python -m venv .venv, uv venv, or pipx for standalone command-line tools.
  • Do not commit virtual environment directories.
  • Record install commands or dependency files so the environment can be recreated.

Primary sources surfaced by T003: Python venv, uv installation, uv environments, and pipx installation.

Focus item 6

Prefer explicit commands over shell aliases

Finding

  • T002 found local shell wrappers that change harness startup behavior.
  • For Codex, the local wrapper selects the high-privilege auto profile; that is too consequential to hide in an alias.
  • T003 found an official Pi-specific alias mechanism, but not a verified cross-harness equivalent.

Recommendation

  • Beginner docs should show explicit commands.
  • If aliases are included, make them optional, short, and harness-specific.
  • Explain exactly what each wrapper changes, especially permissions and sandboxing.

Primary source surfaced by T003: Pi shell aliases. Local alias evidence is summarized in T002 without publishing unrelated private shell configuration.

Beginner path

A clearer setup story

  1. Start simple: try chat tools before asking an agent to change files.
  2. Use one agentic tool on one real project: learn how it asks for permission and how to review changes.
  3. Keep commands explicit: avoid hidden aliases until the user understands what they change.
  4. Use isolated environments: prefer documented virtual environments or CLI installers over machine-specific paths.
  5. Add advanced guards deliberately: hooks and high-privilege profiles belong behind an opt-in warning.
  6. When delegating work: use task files, fresh context, and handoff notes; choose the harness-specific subagent method only after the baseline is understood.
